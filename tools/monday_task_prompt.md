You are refreshing the CCGL Wholesale CRM for the week and sending the team's Monday brief. Work only inside the connected "CCGL Wholesale" folder, in its `ccgl-crm` subfolder (a git repo; in the sandbox it appears under the mounted folder, e.g. `<mount>/CCGL Wholesale/ccgl-crm`). Run every command from that folder with `python3`. Do NOT run any git command yourself: git on this Mac is done by launchd jobs outside the sandbox — a pull at 6:45 AM and a push at 7:45 AM on Mondays, and on demand whenever an empty file named `pull` or `push` appears in tools/out/requests/ (the job com.ccgl.crm.sync-request serves it and deletes the file; Steps 0 and 5 use this, and it is what lets a manual re-run of this task work on any day). Do NOT edit index.html, and do NOT touch data/users.json or data/activities/. Never send email to anyone other than the addresses in tools/weekly_email_config.json (or Dan alone on failure).

Step 0 — sanity. Confirm the folder exists and that data/accounts.json, data/orders.json, data/contacts.json, data/leads.json and data/qbo.json all parse as JSON (`python3 -c "import json;[json.load(open('data/'+f+'.json')) for f in ('accounts','orders','contacts','leads','qbo')]"`). If the folder isn't connected or a file is broken, skip to the failure step. Then make sure the repo has today's pull, so the brief is built on this week's orders and activity rather than last week's. A pull counts when tools/out/sync.log has a line that starts with `=== ` plus today's date in Eastern time and ends with ` pull`, and the lines after it do not say `PULL FAILED`. Check with `grep "=== $(TZ=America/New_York date +%F) .* pull" tools/out/sync.log; tail -8 tools/out/sync.log`. If there is no such line (normal on any day but Monday — the 6:45 job only runs Mondays) or the latest one failed, request a pull: `mkdir -p tools/out/requests && touch tools/out/requests/pull`. Wait for it with `for i in $(seq 1 12); do [ -e tools/out/requests/pull ] || break; sleep 10; done; tail -8 tools/out/sync.log` — the request file disappears when the pull has been served. Judge by the log: if it now shows a `=== <today> HH:MM pull` block with no PULL FAILED after it, continue (even if the request file still shows in a listing — the folder view can lag). If no new pull line appeared after 2 minutes, or it says PULL FAILED, go to the failure step and say which: nothing served means the launchd job com.ccgl.crm.sync-request on the mini is not loaded or /bin/bash lost Full Disk Access; a failed pull means git itself refused (quote the error from the log). Never build the brief on a stale repo.

Step 1 — QuickBooks pull, using the ccgl-qbo connector's run_qbo_query tool. First check the connection with `SELECT Id FROM Customer MAXRESULTS 1` (use this query, not the test_connection tool, as the check). If it fails, go to the failure step with the full error text and add this line to the email: "The mini's QuickBooks sign-in is probably stale. On the MacBook, look at ~/ccgl_qbo/token_sync.log to see when the two Macs last synced, then run: scp ~/ccgl_qbo/config.json dgai-1@100.72.159.85:ccgl_qbo/config.json and re-run this task." If the check passes, run exactly these two queries:
  (a) SELECT Id, TxnDate, DocNumber, TotalAmt, Balance, DueDate, CustomerRef, ShipAddr FROM Invoice WHERE TxnDate >= '2026-01-01' ORDERBY TxnDate DESC MAXRESULTS 1000
  (b) SELECT Id, DisplayName, Balance FROM Customer WHERE Active = true MAXRESULTS 1000
The invoice result is large and will be saved by the tool to a file. If that file is on the same machine as the repo, pass its path straight to the ingest script. If this session runs in the cloud (the saved file is in the cloud workspace, not on the Mac), copy it to /mnt/user-data/outputs/ccgl_refresh/_raw_invoices.json and write it into the repo at tools/qbo_raw/_raw_invoices.json with the device_commit_files tool. The customer result usually comes back inline: write every row (Id, DisplayName, Balance) to tools/qbo_raw/_raw_customers.json the same way, and check it before ingesting — the row count must equal the result's maxResults, the id-to-name pairs must match the previous tools/qbo_raw/customers.json apart from genuinely new or renamed customers, and the sum of the positive balances must equal the total open Balance of the invoice pull. Then run:
  python3 tools/qbo_ingest.py invoices <path-to-invoice-result>
  python3 tools/qbo_ingest.py customers <path-to-customer-result>
The ingest script refuses a pull that is much smaller than last time — if it refuses, retry the query once; if it still refuses, stop and go to the failure step (don't rebuild on partial data).

Step 2 — rebuild the feed: `python3 tools/build_qbo.py`. It prints counts (invoices, $ invoiced, open, past due, mapped/unmapped customers) and lists any UNMAPPED QuickBooks customers. Do not edit tools/qbo_map.json yourself; unmapped customers just appear on the Insights tab for Dan.

Step 2b — reconcile the order list to QuickBooks: `python3 tools/qbo_sync.py --apply`. QuickBooks is the master for what was sold. The script pairs new invoices with tracker orders, sets each paired order's date, total and location from its invoice (stamping the invoice number), creates orders for invoices nobody logged in the tracker (source QBO), and flags confirmed orders that have had nothing invoiced for 21+ days as "no invoice". It prints one line like `qbo_sync: 3 ADJUST, 1 CREATE from invoice, 2 MATCH` or `qbo_sync: nothing to do`; it never deletes anything. Then run `python3 tools/build_qbo.py` once more so the Insights reconciliation card reflects the links. Include the qbo_sync line in the final report, and name any "no invoice" flags and any CREATE rows so Dan can check them.

Step 3 — assessments. Run `python3 tools/weekly_facts.py` and read the whole fact sheet (orders last 7 days, revenue at risk, due this week, past due, rising, fading, top 10, unassigned, one-and-done, activity by rep, open next steps, reconciliation, placeholder rows). Then write tools/assessments.json: a JSON list of 12–18 objects, each {"account": "<exact name from accounts.json or null>", "town": "<exact town or null>", "priority": "critical|high|medium|low", "kind": "risk|coverage|due|rising|protect|winback|hygiene|pipeline|ar", "headline": "<one line, specific, with a number>", "assessment": "<2–4 sentences using only figures from the fact sheet — what the numbers say and why it matters>", "action": "<who does what this week: 'Joey: …', 'Matt: …', 'Dan: …', 'Charley: …'>"}. Cover, in this order of importance: the biggest revenue at risk (quiet accounts, largest first), accounts due for reorder this week worth a call, past-due balances that should be checked before the next delivery (owner named), rising accounts to protect or expand, fading accounts and one-and-done accounts worth a win-back, coverage gaps (large unassigned accounts, overdue next steps), and one or two hygiene notes (placeholder order rows, unmapped QuickBooks customers, blank tracker totals). Owners: Joey is the rep, Matt is the sales director, Charley runs fulfillment/delivery, Dan is finance. Be direct and concrete; no filler. Use "account"/"town" values exactly as they appear in the fact sheet (the part before " / " is the name, after it the town; use null town only when the account has none). Then run `python3 tools/make_insights.py` — it validates names and writes data/insights.json. If it exits with an error naming an account it can't find, fix that entry (check data/accounts.json for the exact spelling) and rerun until it prints "insights.json: N assessments".

Step 4 — the Monday brief text. Run `python3 tools/weekly_email.py` (no flags); it prints the subject and writes tools/out/weekly_email.txt. Read that text file and sanity-check the numbers: orders last week should be a plausible count (0–60) and the QuickBooks invoiced total should be at least what it was before this run (compare with the totals printed by build_qbo.py); if something looks wrong, do not send the brief — go to the failure step. Do not send yet.

Step 5 — publish, so the dashboard link in the brief already shows this week's numbers. Run `python3 tools/make_preview.py` (rebuilds the offline preview; ignore any error here). Then request a push: `touch tools/out/requests/push`, and wait for it the same way: `for i in $(seq 1 12); do [ -e tools/out/requests/push ] || break; sleep 10; done; tail -12 tools/out/sync.log`. A good push shows a `=== <today> HH:MM push` block that ends with a line like `   abc1234..def5678  main -> main` or `Everything up-to-date`. If it shows PUSH FAILED, or no push line appeared after 2 minutes, carry on to Step 6 anyway and say so in the final report — the 7:45 AM Monday job will push again, and Dan can push by hand.

Step 6 — send the brief by running `python3 tools/weekly_email.py --send` exactly once — the script itself emails the team over Gmail SMTP as "CCGL CRM Weekly Update" with the logo embedded, using credentials already stored on this Mac (~/.ccgl_crm_smtp.json). Success prints a line starting with "SENT as". Do NOT also send it with the Gmail connector. If the --send run errors (missing credentials, Gmail rejected the login), go to the failure step and include the error text.

Failure step — if any of steps 0–4 or 6 failed (a failed push in Step 5 is reported, not fatal), send ONE short plain-text email from the Gmail connector to dan@capecodgrowlab.com only, subject "CCGL Monday refresh — needs a look", saying which step failed and the exact error text, and stop. Do not send the team brief on a failed run. Before writing that email, read the project doc claude/ccgl-monday-refresh-notes.md — it lists the failures seen so far and what fixed each one — and include the matching fix in the email.

Finish by reporting, in a few lines: invoices pulled and $ invoiced, open and past-due totals, what qbo_sync changed (orders created, adjusted, flagged), number of assessments written, whether the data was published (Step 5) and whether the brief was sent and to whom, and anything Dan should look at (unmapped customers, failures).
